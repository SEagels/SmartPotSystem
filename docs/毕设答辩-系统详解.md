# SmartPot 智能花盆系统 — 毕设答辩详解

## 一、系统概述

SmartPot 是一套**基于物联网的智能花盆系统**，由三大部分组成：

| 层级 | 技术 | 职责 |
|------|------|------|
| **感知层（硬件）** | ESP32-S3 + 传感器 + 摄像头 + 水泵 | 环境数据采集、执行控制指令、本地自动补水 |
| **网络层** | MQTT + HTTPS | 设备与云端之间的实时消息通信 + 图片上传 |
| **应用层（云端+前端）** | FastAPI + YOLOv11 + React | 数据存储与分析、AI 病害检测、用户交互界面 |

**一句话总结**：ESP32 采集花盆环境数据，通过 MQTT 上报云端，用户通过 Web 控制台远程监控植物状态、查看 AI 病害检测结果、远程浇水和拍照。

## 四、各层详细设计

### 4.1 硬件层（ESP32-S3 固件）

#### 主循环时序

```
┌─ setup() ──────────────────────────────────────────┐
│ Serial 初始化 → WiFi 连接 → NTP 对时 →              │
│ 传感器初始化 → 摄像头初始化 → 水泵初始化 →           │
│ MQTT 连接 → HTTP 服务启动 → 上报设备上线             │
└─────────────────────────────────────────────────────┘
                        ↓
┌─ loop() ───────────────────────────────────────────┐
│ WiFi 维护 ──→ MQTT 维护 ──→ HTTP 请求处理           │
│   ↓                                                 │
│ 每 5s：传感器读取（DHT11 + BH1750 + 土壤湿度）       │
│ 每 5min：遥测数据上报（MQTT publish）               │
│ 持续：自动补水检查（土壤<25% 且 温度<38°C → 开泵8s） │
│ 每 30s：串口状态打印                                │
```

#### 病害检测流水线

```
1. 图片上传 → 存储(本地/MinIO) → DB 状态标记为 pending_detection
2. ImageProcessor 每 10s 轮询，每次取 5 张待检测图片
3. YOLOv11 PyTorch 模型推理（640×640, NMS, 12类中文病害名）
   ↓ 模型不可用时降级
4. 规则检测（RGB 颜色直方图启发式, 置信度 0.4-0.6）
5. 检测结果入库（bbox 坐标、置信度、严重程度(mild/moderate/severe)、防治建议）
6. 置信度 ≥ 0.7 → 自动生成告警
7. 健康评分 = 100 - (病害数×20 + 最高置信度×30)，范围[10, 100]
```

ALS（早疫病）、Angular Leafspot（角斑病）、Anthracnose Fruit Rot（炭疽果腐）、Bean Rust（豆锈病）、Blossom Blight（花枯病）、Gray Mold（灰霉病）、Leaf Spot（叶斑病）、Powdery Mildew Fruit（白粉病-果实）、Powdery Mildew Leaf（白粉病-叶片）、disease（一般病害）、leaf mold（叶霉病）、spider mites（红蜘蛛）

#### 关键设计要点

| 要点 | 实现方式 |
|------|---------|

## 五、高频考点（答辩老师可能提问）

### 架构与协议类

**Q1: 为什么选择 MQTT 而不是 HTTP 做设备通信？**

> MQTT 是发布/订阅模型，专为物联网设计：二进制协议头部仅 2 字节，带宽开销极低；支持 QoS 三级服务质量保证；双向通信让设备既能上报数据也能接收云端指令；心跳保活机制天然支持离线检测。HTTP 用于图片上传（大二进制数据不适合 MQTT），两者互补。

**Q2: MQTT QoS 0/1/2 的区别？你用的哪个？为什么？**

> QoS 0：最多一次（不保证送达）；QoS 1：至少一次（可能重复）；QoS 2：恰好一次。本系统用 QoS 1，在可靠性和开销之间平衡——遥测数据允许偶有重复（可根据时间戳去重），但不能丢失。

**Q3: 图片为什么走 HTTPS 而不是 MQTT？**

> ESP32 的 PubSubClient 库默认最大报文仅 1024 字节，一张 JPEG 图片轻易超过。且 MQTT 设计初衷是传输小消息，大文件会阻塞其他消息的收发。HTTP multipart 是文件上传的标准方式。

### 数据库与存储类

**Q4: SQLite 为什么要加写锁？**

> SQLite 默认支持多读但只支持单写。本系统有多个异步协程同时写入（MQTT 遥测入库、图片上传、检测结果写入），使用 `asyncio.Lock` 确保同一时刻只有一个协程执行写操作。同时开启 WAL 模式（Write-Ahead Logging），写操作追加到 WAL 文件，读操作不受写操作阻塞。

**Q5: 为什么生产环境用 TimescaleDB 而不是普通 PostgreSQL？**

> TimescaleDB 是专为时序数据设计的 PostgreSQL 扩展：自动按时间分区（hypertable）、内置 `time_bucket()` 等聚合函数、旧数据自动压缩节省存储、连续聚合物化视图使日/周统计毫秒级响应。传感器数据（5min × 多设备）是典型时序场景。

**Q6: SQLAlchemy AsyncConnection 和 AsyncSession 的区别？**

> AsyncConnection (engine.begin()) 是底层连接对象，不支持 ORM 操作如 `session.add_all()`。AsyncSession (sessionmaker()) 是完整 ORM 会话，支持增删改查、关系加载、工作单元模式。本项目踩过这个坑：在 seed_data 中用 engine.begin() 然后调用 add_all() 会报 AttributeError。

### 检测算法类

**Q7: 为什么用 YOLOv11？相比传统图像处理有什么优势？**

> YOLOv11 端到端同时完成目标定位和分类，无需手动设计特征；FPN+PAN 多尺度结构能检测不同大小的病斑；深度学习对光照变化、复杂背景更鲁棒。传统方法（颜色阈值、形态学）难以泛化到不同植物和光照条件。

**Q8: 知识蒸馏是什么？在你的项目中怎么用的？**

> 知识蒸馏是模型压缩技术，用大模型（教师）的软标签指导小模型（学生）学习。本项目用原始 YOLOv11 作教师，剪枝后模型作学生，通过 MGD（Masked Generative Distillation）损失函数传递知识。剪枝减小模型体积和推理时间，蒸馏弥补精度损失。

**Q9: 健康评分公式是怎么设计的？**

> `health_score = 100 - (disease_count × 20 + max_confidence × 30)`，结果限制在 [10, 100]。病害种类越多、置信度越高，分数越低。例如检测到 2 种病害且最高置信度 0.85 → 100 - (40 + 25.5) = 34.5，属于不健康状态。

### 系统设计与可靠性类

**Q10: 开发模式和生产模式设计的目的？**

> 遵循 12-Factor App 方法论。开发模式一个 `uvicorn` 命令即可启动全部功能（SQLite + 内嵌 MQTT Broker + 本地存储），方便开发和演示。生产模式各组件独立部署（PostgreSQL + EMQX + MinIO + Redis），支持横向扩展和高可用。通过 `ENVIRONMENT` 环境变量统一切换。

**Q11: 指令下发后如何保证可靠性？**

> 命令-应答模式 + ACK 超时机制：后端通过 MQTT 下发指令 → ESP32 执行后发布响应消息 → 后端启动 30s 超时计时器。收到 ACK 标记 executed，超时标记 timeout。所有 Command 记录持久化到数据库，可完整追溯。

**Q12: ESP32 断网后自动补水还能工作吗？**

> 能。自动补水逻辑是 ESP32 本地自主决策的：`if (土壤湿度 < 25% && 温度 < 38°C && 距上次浇水 ≥ 2min) { 开泵8s }`。即使 WiFi/MQTT 完全断开，本地自动补水仍然正常工作。

**Q13: 设备在线的判断逻辑？**

> 复合判断：不仅看 MQTT 连接状态，还检查最近一条遥测记录是否在**10 分钟以内**。防止 MQTT 会话残留导致的"假在线"误判。

### 安全类

**Q14: 系统有哪些安全措施？**

> JWT 令牌认证（HS256, 7天过期）、bcrypt 密码哈希（不存明文）、设备归属级联验证（`get_current_device` 检查 device.user_id == current_user.id）、ESP32 图片上传用预共享密钥、Pydantic 自动参数校验。生产环境还需收紧 CORS 策略。

### 前端类

**Q15: 前端怎么做实时数据更新？**

> `useWebSocket` 自定义 Hook 管理 WebSocket 单例连接（`ws://host:8000/v1/ws?token=<jwt>`），5 秒断线自动重连。后端按 user_id 广播事件（telemetry_update、device_status、watering_complete 等），前端各页面通过 deviceId 过滤关注的事件类型。

### 开放/综合类

**Q16: 这个系统还可以怎么改进？**

> - ESP32 低功耗：加入 Deep Sleep + 定时唤醒（当前持续运行）
> - OTA 固件升级：MQTT 下发固件 URL，ESP32 HTTP OTA
> - 边缘推理：剪枝后 YOLO 部署到 ESP32-S3（利用其神经网络加速器）
> - 多通道通知：邮件/短信/微信推送告警
> - BLE 本地配网：蓝牙辅助 WiFi 配置
> - 测试覆盖率：后端和固件测试可进一步提高

**Q17: Python 3.14 的 `datetime.UTC` 跟你代码里的 `from datetime import UTC` 有什么关系？**

> Python 3.14 中 `datetime.datetime` 类不再有 `UTC` 属性。正确写法是 `from datetime import UTC` 直接引用模块级常量 `UTC`，而非 `datetime.UTC`。这是本项目踩过的兼容性坑。
