# 05 — 无设备码的设备发现与绑定方案

## 结论

当前项目里 ESP32 已经和电脑/后端在同一个 WiFi 下，优先采用 **WiFi 局域网发现 + 后端绑定**，暂不采用 BLE。

原因：

- ESP32 固件已经提供本地 HTTP 服务，`GET /api/status` 会返回 `device_id`、IP、固件版本、RSSI 等信息。
- 后端运行在同一局域网时可以主动扫描 ESP32，避免浏览器/Android 直接访问 ESP32 产生 CORS、明文 HTTP、权限差异问题。
- Android 使用 BLE 需要位置/附近设备权限、配对状态处理和额外固件 GATT 服务；在设备已经入网的前提下复杂度更高。

BLE 更适合“设备还没有 WiFi 账号”的首次配网场景。若后续要做量产级配网，可在本方案前面增加 BLE 配网步骤。

## 绑定流程

1. ESP32 通电并连接到与电脑/后端相同的 WiFi。
2. ESP32 本地 HTTP 服务保持开启：`http://<device-ip>/api/status`。
3. 前端或 Android App 调用后端：

```http
GET /v1/devices/lan-discover?cidr=172.20.10.0/24
Authorization: Bearer <jwt>
```

如果不传 `cidr`，后端会按本机私有 IPv4 地址自动扫描对应 `/24` 网段。

4. 后端并发探测每个候选 IP 的 `/api/status`，返回发现的设备：

```json
[
  {
    "device_id": "SP000001",
    "ip": "172.20.10.8",
    "firmware_version": "v1.0.0",
    "wifi_rssi": -48,
    "uptime_s": 32,
    "mock_mode": false,
    "pump_running": false
  }
]
```

5. 用户在列表里选择设备并确认绑定：

```http
POST /v1/devices/lan-bind
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "device_id": "SP000001",
  "ip": "172.20.10.8",
  "name": "客厅智能花盆"
}
```

6. 后端再次访问该 IP 的 `/api/status`，确认返回的 `device_id` 与用户选择一致，然后创建或绑定设备记录。

## 安全边界

没有机身设备码、屏幕、独立按钮或二维码时，系统无法做到强所有权证明。本方案的所有权依据是：

- 用户已登录；
- 后端能在私有局域网访问到该 ESP32；
- 绑定时再次探测设备，防止手动输入错误 IP。

如果要进一步增强确认，可以增加一个“短时间配对窗口”：ESP32 上电后 5 分钟内允许 `lan-bind`，超时后只允许已绑定用户控制。

## 已新增后端接口

- `GET /v1/devices/lan-discover`
- `POST /v1/devices/lan-bind`

这两个接口不会影响原有 `POST /v1/devices/bind` 的设备编号 + 绑定码流程。
