# 智能盆栽系统毕设答辩可能问题

> 适用场景：答辩前自问自答、准备 PPT 讲稿、被老师追问技术细节时快速定位回答思路。

## 一、项目总体与选题价值

### 1. 你的项目解决了什么问题？

本项目解决的是家庭盆栽养护中“不会判断环境状态、忘记浇水、病害发现晚、养护建议不专业”的问题。系统通过 ESP32-S3 采集温湿度、土壤湿度、光照和植物照片，后端进行数据存储、病害识别、告警生成和养护建议分析，Web 端和 Android App 端用于用户查看和远程控制。

核心价值是把传统盆栽养护从“人工经验判断”变成“传感器数据 + 图像识别 + 自动补水 + 智能建议”的闭环系统。

### 2. 为什么选择智能盆栽作为毕设题目？

这个题目比较适合作为毕业设计，因为它覆盖了嵌入式、物联网通信、后端服务、数据库、前端可视化、移动端和人工智能识别等多个方向，能够体现完整系统开发能力，而不是只做单一页面或单一算法。

同时，智能家居和智慧农业都有实际应用场景，盆栽是一个规模较小但功能闭环完整的对象，适合在有限时间内完成原型验证。

### 3. 项目的创新点在哪里？

可以从以下几个角度回答：

- 多端协同：ESP32-S3 固件、FastAPI 后端、React Web 端、Android App 端共用一套接口。
- 多源感知：融合温湿度、土壤湿度、光照、图像等数据。
- 自动控制闭环：根据植物品种阈值和土壤湿度触发自动补水。
- 图像识别：通过 YOLO/ONNX 模型对植物病害图片进行检测。
- 养护建议：结合传感器状态、植物品种和检测结果生成养护建议。
- Mock 模式：无硬件情况下也可以进行固件预开发和接口联调。

### 4. 这个系统和普通的温湿度监控有什么区别？

普通温湿度监控只做数据展示，而本系统包含完整闭环：

- 采集：传感器和摄像头采集环境与图像。
- 传输：设备通过 MQTT/HTTP 上传数据。
- 分析：后端进行病害检测、告警判断、养护建议生成。
- 控制：后端可以下发补水、拍照等命令。
- 展示：Web 和 App 实时展示状态、历史曲线、告警和图片。

所以它不是简单监控，而是“监测 + 分析 + 决策 + 控制”的智能养护系统。

## 二、系统架构与通信设计

### 5. 你的系统整体架构是什么？

系统采用三层架构：

```text
ESP32-S3 设备层 -> FastAPI 后端服务层 -> React Web / Android App 应用层
```

设备层负责传感器采集、摄像头拍照和水泵控制；后端负责认证、设备管理、数据存储、病害检测、告警和命令调度；前端和 App 负责用户交互和数据可视化。

### 6. 为什么设备数据使用 MQTT，而图片使用 HTTP？

传感器数据体积小、频率固定，适合用 MQTT。MQTT 有发布订阅机制，轻量、低开销，适合物联网设备持续上报遥测数据。

图片体积大，不适合通过 MQTT 传输。图片通过 HTTP multipart 上传更稳定，也更容易和后端文件存储、图片处理流程结合。因此本项目采用“遥测数据走 MQTT/HTTP，图片走 HTTP 上传”的方式。

### 7. 为什么 Web 端使用 WebSocket？

如果 Web 端定时轮询后端，会产生大量无效请求，而且实时性较差。WebSocket 可以让后端在遥测更新、告警生成、命令状态变化、病害检测完成时主动推送消息给前端。

这样用户不需要刷新页面，也能及时看到设备状态变化。

### 8. REST API、MQTT、WebSocket 分别负责什么？

- REST API：用户登录、设备管理、植物品种管理、图片上传、历史数据查询等请求响应型业务。
- MQTT：设备周期性上报遥测数据，以及后端向设备下发控制命令。
- WebSocket：后端向 Web 端实时推送状态变化。

三者不是重复设计，而是分别适配不同通信场景。

### 9. 为什么后端选择 FastAPI？

FastAPI 支持异步接口，性能较好，适合同时处理设备数据、前端请求、图片上传和后台任务。它还基于 Pydantic 做数据校验，接口文档可以自动生成，适合毕业设计中展示接口规范和系统工程性。

### 10. 为什么开发环境用 SQLite，生产环境设计 PostgreSQL/TimescaleDB？

SQLite 部署简单，适合毕设开发和演示，不需要额外安装数据库服务。生产环境中设备数量和时序数据量会增加，因此更适合使用 PostgreSQL，并通过 TimescaleDB 管理传感器历史数据。

答辩时可以强调：本项目开发模式优先保证可运行，架构上预留了生产数据库切换能力。

## 三、设备绑定与新增设备发现

### 11. 设备没有设备码，如何确认新增设备？

本项目的思路是让 ESP32 和用户电脑或手机处于同一 WiFi 网络下，设备启动后开放局域网发现接口。前端或 App 可以在局域网中扫描可用设备，读取设备返回的基础信息，例如设备名称、IP、MAC 派生 ID、固件版本和绑定状态。

用户点击发现到的设备后，后端完成绑定关系创建。这样可以避免人工输入设备编号和验证码。

### 12. WiFi 发现和 BLE 发现哪个更适合？

当前项目更适合 WiFi 局域网发现，因为 ESP32 已经和电脑处于同一 WiFi 下，Web 端和 App 端可以通过局域网 HTTP 接口发现设备，开发成本低，调试方便。

BLE 更适合“第一次给设备配网”的场景，例如设备还没有接入 WiFi，需要手机通过蓝牙把 WiFi 名称和密码发给设备。后续如果扩展为商业化产品，可以采用“BLE 配网 + WiFi 通信”的组合方案。

### 13. 如何避免用户绑定到别人的设备？

可以通过以下方式增强安全性：

- 只允许未绑定设备被发现和绑定。
- 绑定时要求设备处于短时间配对模式，例如上电后 3 分钟内可绑定。
- 设备端生成一次性随机 token，绑定完成后失效。
- 后端保存设备和用户的归属关系，后续所有接口都校验用户是否拥有该设备。

当前毕设原型重点验证流程，后续可继续增强配对安全。

## 四、设备在线状态与时效性

### 14. 设备断电后为什么以前还会显示在线？

这是因为原来的在线状态可能只依赖数据库中的 `status` 字段，没有结合最近一次心跳时间判断。设备断电后，如果没有新消息更新状态，后端仍可能保留旧的在线状态。

### 15. 现在如何判断设备是否在线？

后端通过 `last_seen_at` 记录设备最近一次上报时间，设备周期性发送心跳或遥测数据。如果当前时间距离 `last_seen_at` 超过设定阈值，例如 75 秒，就认为设备离线。

这种机制比单纯保存 `online/offline` 字段更可靠，因为它基于时间有效性判断。

### 16. 为什么不能只靠前端判断在线状态？

前端只负责展示，不能成为可信状态源。如果每个客户端都自己判断，容易出现多个端显示不一致。在线状态应由后端统一根据设备心跳和最近上报时间计算，然后提供给 Web 和 App。

## 五、自动补水与植物阈值

### 17. 自动补水逻辑是怎么设计的？

系统会根据设备绑定的植物品种读取该植物的土壤湿度阈值。当传感器上报的土壤湿度低于阈值时，后端或设备端可以触发补水命令，控制水泵运行指定时间。

例如植物阈值为 30%，当前土壤湿度为 20%，则可以触发自动补水；如果阈值设置为 1%，当前湿度为 20%，则不应该补水。

### 18. 为什么植物品种需要配置补水阈值？

不同植物对水分需求不同。多肉类植物耐旱，阈值可以低一些；绿萝、薄荷等植物对水分需求更高，阈值可以高一些。把阈值放到植物品种表中，可以让设备根据植物类型自动调整养护策略。

### 19. 阈值是在后端判断还是固件判断？

两种方式都可以。本项目中后端负责保存植物品种和阈值配置，并同步到设备运行配置。设备端可以在本地执行自动补水，这样即使后端暂时不可用，也能保持基本养护能力。

更合理的设计是：后端统一管理配置，设备本地执行实时控制。

### 20. 如何避免水泵频繁启动？

可以加入以下保护机制：

- 最小补水间隔，例如两次补水至少间隔 10 分钟。
- 单次补水最大时长。
- 补水后延迟重新判断，让水分渗透后再采样。
- 记录补水事件，方便追踪异常。

这些机制可以避免传感器波动导致水泵反复启停。

## 六、固件与硬件设计

### 21. ESP32-S3 固件主要做了哪些事情？

固件主要负责：

- WiFi 自动连接和重试。
- 初始化 DHT、BH1750、土壤湿度 ADC、OV2640 摄像头和水泵。
- 周期性采集传感器数据。
- 上传遥测数据和图片。
- 接收后端命令，例如补水、拍照、同步配置。
- 提供 HTTP 控制和发现接口。
- 支持 Mock 模式，在没有硬件时返回模拟数据。

### 22. 为什么要支持 Mock 模式？

因为毕设开发早期可能没有完整硬件，或者硬件还没有焊接调通。Mock 模式可以让固件在无传感器、无摄像头的情况下仍然编译运行，并返回模拟传感器数据和假图片。

这样后端、前端、App 都可以提前联调，降低硬件进度对软件开发的影响。

### 23. 摄像头引脚为什么不能随便改？

OV2640 摄像头和 ESP32-S3 的连接依赖固定 GPIO 映射，错误的引脚会导致摄像头初始化失败或拍照失败。项目中把引脚统一定义在 `firmware/include/board_pins.h`，可以避免不同模块重复定义和误用。

### 24. 水泵控制为什么要支持 active_high 和 active_low？

不同继电器或驱动模块的触发电平可能不同。有些模块高电平打开，有些模块低电平打开。支持 active_high/active_low 可以提高固件适配性，避免换驱动板时大改代码。

## 七、后端与数据库

### 25. 后端分层结构是怎样的？

后端主要分为：

- `api/`：FastAPI 路由层，负责请求解析和响应返回。
- `services/`：业务逻辑层，处理设备、遥测、图片、病害、植物、告警等业务。
- `models/`：SQLAlchemy ORM 数据模型。
- `schemas/`：Pydantic 请求和响应模型。
- `core/`：数据库、JWT、安全、MQTT、WebSocket 等基础设施。
- `worker/`：后台任务，例如图片检测、自动补水、定时拍照、遥测消费。

这种分层可以让接口、业务和数据模型相对独立，便于维护。

### 26. 为什么使用异步 SQLAlchemy？

后端需要同时处理前端请求、设备上报、图片任务和后台 worker。异步数据库访问可以减少阻塞，提高并发处理能力。

不过 SQLite 本身并发写能力有限，所以开发环境中需要注意写锁和事务控制；生产环境更建议使用 PostgreSQL。

### 27. 主要数据库表有哪些？

主要有：

- `User`：用户。
- `Device`：设备。
- `Telemetry`：传感器遥测数据。
- `Image`：设备拍摄或上传的图片。
- `Detection`：病害检测结果。
- `Alert`：告警记录。
- `Command`：设备控制命令。
- `WateringEvent`：补水事件。
- `PlantType`：植物品种及养护阈值。

这些表共同支撑设备管理、历史曲线、图片识别、自动补水和告警中心。

### 28. JWT 在项目中起什么作用？

JWT 用于用户认证。用户登录成功后，后端返回 token，前端和 App 后续请求都带上 Bearer token。后端通过 token 解析用户身份，并校验用户是否有权访问某个设备。

### 29. 如何保证用户不能访问别人的设备？

后端在设备相关接口中会根据当前登录用户和设备 ID 查询设备。如果设备不属于该用户，则返回无权限或不存在。也就是说，权限校验不是靠前端隐藏按钮，而是在后端接口中完成。

## 八、图像识别与病害检测

### 30. 病害检测流程是什么？

流程如下：

1. 设备或用户上传图片。
2. 后端保存图片，并将状态标记为待检测。
3. 后台图片处理 worker 读取待检测图片。
4. 图像质量评估和必要的图像增强。
5. 调用 YOLO/ONNX 模型进行病害检测。
6. 保存检测框、类别、置信度和建议。
7. 生成告警并推送给前端。

### 31. 为什么使用 ONNX 模型？

ONNX 是通用模型格式，部署时不强依赖训练框架内部结构。相比直接加载 `.pt` 文件，ONNX 更适合推理部署，也减少了因为训练环境和部署环境不一致导致模型无法加载的问题。

### 32. 图像增强的目的是什么？

摄像头拍摄时可能存在光线不足、对比度低、画面模糊等问题，这会影响识别效果。后端可以对低质量图片进行亮度、对比度、锐度等处理，提高图像可见性。

但增强不是越强越好。过度增强可能造成颜色偏移，反而降低识别准确率。因此项目中会比较原图和增强图的质量与检测结果，选择更适合用于展示和检测的图片。

### 33. 质量评分是依据什么？

质量评分主要依据图像的亮度、对比度和清晰度。可以这样解释：

- 亮度：图片是否过暗或过曝。
- 对比度：植物和背景、叶片纹理是否区分明显。
- 清晰度：通过边缘和细节变化判断是否模糊。

项目中质量评分是一个工程化指标，用来辅助判断图片是否适合识别，不等同于模型的病害置信度。

### 34. 为什么识别率不高？

识别率主要受以下因素影响：

- 训练数据和实际 ESP32 摄像头图片分布不一致。
- 光照、角度、背景、焦距和清晰度变化较大。
- 数据集规模不足或类别不平衡。
- 某些病害在早期视觉特征不明显。
- 盆栽真实场景比公开数据集更复杂。

### 35. 如何提高识别准确率？

最有效的方法是重新收集真实场景数据并微调模型，尤其要使用 ESP32 摄像头拍摄的数据。还可以：

- 固定拍摄角度和补光条件。
- 增加低光、反光、模糊、遮挡等数据增强。
- 增加健康叶片和误检样本。
- 调整置信度阈值和 NMS 参数。
- 对低质量图片先提示重新拍摄，而不是强行识别。

### 36. 置信度阈值如何解释？

可以回答为：系统设置置信度阈值是为了减少低置信度误报。低于阈值的检测结果不直接作为病害结论，而是视为“未发现可靠病害证据”。高于阈值的结果才生成病害记录和告警。

答辩时不要把置信度显示优化说成“提高模型准确率”，更合适的说法是“结果后处理和低置信度拒识机制”。

### 37. 病害识别失败时系统怎么办？

如果模型不可用或检测失败，后端会记录错误状态，不影响设备数据和其他功能。后续可以通过重新检测、替换模型或回退规则继续处理。

## 九、前端与 Android App

### 38. Web 端主要有哪些功能？

Web 端主要包括：

- 登录注册。
- 设备概览。
- 设备详情。
- 历史曲线。
- 图片和病害检测结果。
- 告警中心。
- 植物品种管理。
- 手动补水和拍照控制。

### 39. 为什么还要做 Android App？

智能家居类系统通常需要移动端入口，用户不一定一直打开电脑。Android App 可以让用户随时查看设备状态、告警和植物信息，也能展示系统的多端适配能力。

### 40. Web 和 App 是否共用接口？

是的。Web 和 App 都通过后端 REST API 访问数据。这样后端是统一的数据和业务中心，多个客户端只负责不同形式的展示。

### 41. 为什么 App 要做毛玻璃和植物主题 UI？

因为这是智能家居和盆栽养护类应用，界面需要体现自然、轻盈、清新的感觉。毛玻璃风格可以让界面更现代，植物主题色可以增强产品一致性，避免界面像普通后台管理系统。

### 42. 底部导航为什么包含设备、告警、植物品种？

这三个模块是用户最常用的核心功能：

- 设备：查看传感器、补水、图片和养护建议。
- 告警：快速处理异常状态。
- 植物品种：维护不同植物的养护阈值。

## 十、安全、部署与测试

### 43. 项目有哪些安全措施？

- 用户密码使用哈希存储。
- 登录后使用 JWT 鉴权。
- 设备接口会校验用户归属。
- 设备端可使用 token 或绑定状态防止非法控制。
- 生产环境应限制 CORS 来源，并使用 HTTPS。

### 44. 当前项目还有哪些不足？

可以诚实回答：

- 病害识别准确率受训练数据影响，仍需更多真实场景数据微调。
- BLE 配网还没有完整实现。
- 水箱水位检测、流量检测等硬件保护还可以扩展。
- SQLite 适合演示，生产环境应切换 PostgreSQL。
- 摄像头成像质量会影响检测稳定性，最好增加补光和固定支架。

### 45. 你如何测试这个系统？

测试分为几个层面：

- 后端：接口测试、数据库读写、图片上传和检测流程测试。
- 前端：页面功能、登录状态、设备详情、历史曲线和告警跳转测试。
- App：登录、设备列表、详情页、告警和植物管理测试。
- 固件：PlatformIO 编译、Mock 模式运行、真实传感器采集、水泵控制和摄像头拍照测试。
- 联调：设备上报数据后，验证后端入库、WebSocket 推送、前端展示是否一致。

### 46. 如果部署到真实环境，需要做哪些调整？

- 使用 PostgreSQL/TimescaleDB 替代 SQLite。
- 使用 Redis、EMQX、MinIO 等服务。
- 开启 HTTPS。
- 配置正式 CORS 域名。
- 使用强随机密钥和设备 token。
- 后端服务使用 Docker 或 systemd 保活。
- 模型推理服务可以独立部署，避免阻塞主接口。

## 十一、答辩高频追问速答

### 47. 老师问：你的系统难点在哪里？

难点主要在多模块联调：设备端要稳定采集和控制，后端要处理设备数据、图片和命令，前端和 App 要实时展示。除此之外，病害识别受真实拍摄条件影响较大，需要进行图像质量控制和模型后处理。

### 48. 老师问：如果设备断网怎么办？

设备端会进行 WiFi 重连。断网期间无法上传数据，但可以保留本地自动补水逻辑。网络恢复后继续上报。后续可以扩展离线缓存，把断网期间的数据补传到后端。

### 49. 老师问：如果传感器数据异常怎么办？

可以设置合理范围校验，例如温度、湿度、光照和土壤湿度都应在物理合理范围内。异常值不直接参与自动控制，而是记录并生成告警。实际项目中还可以做滑动平均或多次采样取中值。

### 50. 老师问：为什么不用纯前端直接控制设备？

纯前端控制设备会带来权限、安全和跨网络问题。后端作为统一控制中心，可以做用户认证、设备归属校验、命令记录、超时管理和状态回传，更符合物联网系统架构。

### 51. 老师问：如何证明系统是闭环的？

可以按这个链路回答：

传感器采集土壤湿度 -> 后端判断低于植物阈值 -> 生成补水命令 -> 设备执行水泵控制 -> 记录补水事件 -> 后续遥测数据反映湿度变化 -> 前端展示状态变化。

这就是从感知到决策再到执行和反馈的闭环。

### 52. 老师问：你的模型和系统业务如何结合？

模型不是单独跑一个分类结果，而是嵌入到了业务流程中。图片上传后进入待检测状态，后台 worker 调用模型检测，检测结果写入数据库，置信度较高时生成告警，同时前端图片详情页展示检测框和养护建议。

### 53. 老师问：你的项目最能体现工程能力的地方是什么？

可以回答：项目不是单点功能，而是完整系统。它包含嵌入式固件、后端 API、数据库设计、实时通信、图像识别、Web 可视化和 Android App，多端通过统一接口协同工作，并且支持 Mock 模式、历史数据、告警和配置同步。

## 十二、答辩表达建议

答辩时建议优先讲清楚三条主线：

1. 数据主线：传感器数据如何从 ESP32 到后端，再到 Web/App 展示。
2. 控制主线：用户或自动策略如何触发水泵控制，设备如何执行并反馈。
3. 图像主线：图片如何上传、增强、识别、生成告警和展示。

如果老师追问细节，优先从“为什么这样设计”和“实际遇到的问题如何解决”回答，不要只背技术名词。
