# SmartPot 智能家居盆栽系统技术总结

本文档用于毕业论文撰写、答辩准备和后续系统介绍。内容围绕本项目的技术栈、系统架构、关键技术点、核心业务流程、实现难点、可写入论文的创新点，以及答辩中可能被问到的问题展开。

---

## 1. 项目概述

SmartPot 是一个面向智能家居场景的智能盆栽养护系统。系统通过 ESP32-S3 采集植物生长环境数据，包括温度、空气湿度、土壤湿度、光照强度，并结合 OV2640 摄像头采集植物图像。设备端通过 MQTT 和 HTTP 与云端后端通信，后端完成设备管理、遥测数据存储、自动补水控制、图像管理、植物病害识别结果管理、告警推送和大模型养护建议生成。用户可以通过 Web 前端和 Android App 查看设备状态、管理植物品种、查看病害照片、接收告警、远程补水和获取养护建议。

系统的目标不是单纯做一个传感器展示平台，而是构建一套完整的“端-云-应用”物联网闭环系统：

- 端：ESP32-S3 固件负责传感器采集、摄像头拍照、水泵控制、本地 HTTP 接口、MQTT 通信。
- 云：FastAPI 后端负责统一 API、设备绑定、数据入库、告警、自动补水、图片与病害记录、大模型建议。
- 应用：React Web 控制台和 Android App 提供可视化监控与交互入口。
- 智能能力：基于图像识别和大模型文本建议，辅助用户进行植物养护决策。

## 3. 系统总体架构

系统采用典型的物联网三层架构：

```text
ESP32-S3 硬件端
  ├─ 传感器采集
  ├─ 摄像头拍照
  ├─ 水泵控制
  ├─ MQTT 遥测/命令
  └─ HTTP 图片上传

        ↓ MQTT / HTTP

FastAPI 云端后端
  ├─ 用户认证
  ├─ 设备管理
  ├─ 遥测数据存储
  ├─ 自动补水判断
  ├─ 图片与病害检测
  ├─ 告警中心
  ├─ 植物品种配置
  ├─ 大模型养护建议
  └─ WebSocket 实时推送

        ↓ REST / WebSocket

Web 前端 / Android App
  ├─ 设备概览
  ├─ 设备详情
  ├─ 传感器数据
  ├─ 远程控制
  ├─ 病害照片
  ├─ 告警中心
  └─ 植物品种管理
```

这种架构的优点是职责清晰：

- 设备端专注采集和执行，减少复杂业务逻辑。
- 后端集中处理数据、业务规则和用户权限。
- 前端和 App 通过统一 API 访问后端，保证多端一致性。
- MQTT 用于低延迟设备通信，REST 用于用户操作和资源管理。

## 4. 核心模块设计

### 4.1 设备端固件模块

固件工程采用模块化结构：

```text
firmware/
  include/
    board_pins.h
    config.h
  src/
    main.cpp
    wifi_manager.cpp/h
    camera_service.cpp/h
    sensor_service.cpp/h
    pump_service.cpp/h
    http_server.cpp/h
    upload_service.cpp/h
    mock_service.cpp/h
    runtime_config.cpp/h
```

各模块职责：

- `board_pins.h`：统一定义所有硬件引脚，避免引脚冲突。
- `config.h`：设备 ID、WiFi、MQTT、HTTP、采样周期和默认参数配置。
- `wifi_manager`：负责 WiFi 自动连接和断线重连。
- `sensor_service`：负责读取 DHT11、BH1750、土壤湿度 ADC。
- `camera_service`：负责 OV2640 摄像头初始化和拍照。
- `pump_service`：负责水泵打开、关闭、运行时长限制和冷却保护。
- `http_server`：提供局域网本地接口，用于设备发现和手动控制。
- `upload_service`：负责 MQTT 连接、遥测上报、命令接收、事件上报和图片上传。
- `mock_service`：无硬件情况下生成模拟传感器数据。
- `runtime_config`：运行时配置中心，用于接收后端下发的自动补水阈值。

### 4.2 后端模块

后端采用分层结构：

```text
backend/app/
  api/          REST API 路由层
  services/     业务逻辑层
  models/       SQLAlchemy ORM 模型
  schemas/      Pydantic 数据模型
  core/         数据库、MQTT、WebSocket、安全等基础设施
  worker/       后台任务
```

分层意义：

- API 层只负责参数接收、依赖注入和响应封装。
- Service 层负责核心业务逻辑，如设备绑定、自动补水、病害处理。
- Model 层对应数据库表结构。
- Core 层封装基础能力，避免业务代码直接依赖底层实现。
- Worker 层用于异步后台任务，避免阻塞 API 请求。

### 4.3 Web 前端模块

Web 前端采用 API 模块、页面组件和可复用组件分离：

```text
frontend/src/
  api/          按业务领域封装 Axios 请求
  pages/        页面级组件
  components/   通用组件
  hooks/        WebSocket、认证等 Hook
  contexts/     登录状态上下文
  styles/       全局主题样式
```

核心页面：

- Dashboard：设备概览、设备卡片、LAN 发现绑定。
- DeviceDetail：设备详情、传感器数据、补水控制、照片和大模型建议。
- Alerts：告警中心。
- PlantTypes：植物品种增删改查。
- DiseaseHistory：病害记录表。
- Reports：养护日报/周报。

### 4.4 Android App 模块

Android App 使用 Jetpack Compose 构建。主要功能：

- 登录页：用户登录，不暴露后端 URL。
- 设备概览：展示设备在线状态、传感器摘要和告警数量。
- 设备详情：展示实时传感器、大模型建议、病害照片、补水和拍照操作。
- 告警中心：聚合所有设备告警，可标记已读。
- 植物品种：查看、添加、修改、删除植物品种。
- 底部导航：概览、告警、品种三大模块切换。

Android 网络层通过 `SmartPotApi.kt` 封装所有后端接口，使用 OkHttp 发起请求，使用 kotlinx.serialization 解析 JSON。

## 5. 关键业务流程

### 5.1 用户登录流程

1. 用户在 Web 或 App 输入用户名和密码。
2. 前端调用 `/v1/auth/login`。
3. 后端校验用户密码。
4. 校验成功后生成 JWT Token。
5. 前端/App 保存 Token。
6. 后续请求通过 `Authorization: Bearer <token>` 访问受保护接口。

技术点：

- JWT 无状态认证。
- bcrypt 密码哈希。
- 前端 Axios 请求拦截器自动附加 Token。
- 后端依赖注入获取当前用户。

### 5.2 设备绑定流程

系统支持两种绑定方式：

1. 传统设备编号 + 绑定验证码。
2. 局域网发现绑定。

局域网发现绑定流程：

1. ESP32 与电脑/后端处于同一 WiFi。
2. 后端扫描局域网设备。
3. ESP32 本地 HTTP 服务返回设备信息。
4. 用户在前端/App 选择发现的设备。
5. 后端将设备与当前用户绑定。

这个设计解决了“硬件设备没有设备码或用户不方便输入设备码”的问题。

### 5.3 遥测数据上报流程

1. ESP32 周期读取传感器。
2. 固件构造 JSON 遥测数据。
3. 通过 MQTT 发布到 `smartpot/{device_id}/telemetry`。
4. 后端 MQTT handler 接收消息。
5. 后端写入 Telemetry 表。
6. 后端通过 WebSocket 推送给在线用户。
7. Web/App 刷新实时数据展示。

遥测数据包括：

- temperature：温度
- humidity：空气湿度
- soil_moisture：土壤湿度
- light_intensity：光照强度
- pump_running：水泵状态
- wifi_rssi：WiFi 信号强度
- uptime_s：设备运行时间

### 5.4 设备在线状态判断

早期问题是设备断电后仍显示在线。修复后采用心跳时效机制：

1. 设备每 30 秒发布一次 MQTT status 心跳。
2. 后端记录 `last_seen_at`。
3. 后端判断设备在线时，不只看 `online=true`，还要判断心跳是否在有效期内。
4. 当前默认超过 75 秒未收到心跳，则认为离线。

技术意义：

- 避免 retained MQTT 状态导致设备假在线。
- 提高在线状态实时性。
- 适合物联网设备弱连接场景。

### 5.5 自动补水流程

系统存在两类自动补水：

#### 云端自动补水

1. 后端 worker 周期检查设备最新土壤湿度。
2. 读取设备绑定植物品种的 `watering_cfg.trigger_soil_moisture`。
3. 如果土壤湿度低于阈值，则下发 MQTT 补水命令。
4. 为避免频繁补水，设置冷却时间。
5. ESP32 执行补水并上报 watering event。

#### 固件本地自动补水

1. ESP32 本地读取土壤湿度。
2. 使用运行时配置中的补水阈值判断是否补水。
3. 阈值由后端通过 MQTT config 指令下发。
4. 新版本默认本地自动补水关闭，防止未同步配置时误补水。

本项目中曾遇到的关键问题：

- 用户将植物品种补水阈值调到 1%，传感器 20% 仍自动补水。
- 原因是固件本地仍使用固定宏 `25%`。
- 修复方式是增加 `runtime_config`，让固件本地自动补水阈值可被后端动态配置。

这是一个非常适合写进论文“问题分析与系统优化”的案例。

### 5.6 远程补水流程

1. 用户在 Web/App 点击补水。
2. 前端调用 `/v1/devices/{device_id}/water`。
3. 后端检查设备是否在线。
4. 后端创建 Command 记录。
5. 后端通过 MQTT 发布 `command/water`。
6. ESP32 收到命令后执行水泵。
7. ESP32 发布命令响应和 watering event。
8. 后端更新命令状态并通过 WebSocket 推送。

### 5.7 摄像头拍照和图片上传流程

1. 用户点击拍照或定时任务触发拍照。
2. 后端通过 MQTT 下发 `command/photo`。
3. ESP32 使用 OV2640 拍照。
4. 图片通过 HTTP multipart 上传到后端。
5. 后端保存图片文件和数据库记录。
6. 图像处理 worker 对图片进行病害检测。
7. 检测完成后保存病害结果并生成告警。

设计原因：

- MQTT 不适合传输大图片文件。
- 图片通过 HTTP 上传更可靠，也便于文件存储和断点分析。
- MQTT 负责控制命令和轻量数据，HTTP 负责大文件。

### 5.8 病害检测流程

1. 图片上传后状态为 `pending_detection`。
2. 后台 worker 轮询待检测图片。
3. 使用 YOLOv11 ONNX 模型进行推理。
4. 识别植物病害类别、置信度和边界框。
5. 保存 Detection 结果。
6. 高置信度病害生成 Alert。
7. Web/App 展示原图、标注图和健康评分。

如果模型不可用，系统可以回退到规则检测逻辑，保证演示阶段功能链路不断。

### 5.9 告警中心流程

告警来源包括：

- 病害识别告警。
- 设备离线告警。
- 补水失败告警。
- 水箱不足告警。
- 传感器异常告警。

告警中心支持：

- 查看所有设备告警。
- 未读/已读状态。
- 单条标记已读。
- 某设备全部标记已读。
- 从告警跳转设备详情。

### 5.10 植物品种管理流程

植物品种包含：

- plant_type：品种代码。
- name：品种名称。
- category：植物分类。
- default_thresholds：温度、空气湿度、土壤湿度适宜范围。
- watering_cfg：补水触发阈值和默认补水时长。

系统支持：

- 添加植物品种。
- 修改植物品种。
- 删除植物品种。
- 设备绑定植物品种。
- 修改品种补水参数后同步到绑定设备。

## 6. 数据库设计关键点

### 6.1 主要数据表

| 表 | 作用 |
|---|---|
| users | 用户账户 |
| devices | 设备信息、绑定关系、在线状态 |
| telemetry | 传感器时序数据 |
| images | 图片记录 |
| detections | 病害检测结果 |
| alerts | 告警记录 |
| commands | 设备命令记录 |
| watering_events | 补水事件记录 |
| plant_types | 植物品种和养护参数 |

### 6.2 设备表关键字段

- `device_id`：设备唯一 ID。
- `user_id`：绑定用户。
- `plant_type`：绑定植物品种。
- `online`：MQTT 状态。
- `last_seen_at`：最后心跳时间。
- `firmware_version`：固件版本。
- `soil_moisture_threshold`：设备当前土壤湿度阈值。
- `watering_max_duration_ms`：最大补水时长。

### 6.3 遥测表关键字段

- `time`：数据时间。
- `device_id`：所属设备。
- `temperature`：温度。
- `humidity`：空气湿度。
- `soil_moisture`：土壤湿度。
- `light_intensity`：光照。
- `pump_running`：水泵状态。
- `wifi_rssi`：WiFi 信号。
- `uptime_s`：设备运行时间。

### 6.4 为什么遥测数据适合 TimescaleDB

传感器数据具有典型时序特征：

- 数据按时间持续增长。
- 查询常按时间范围筛选。
- 需要做聚合，如小时平均、每日平均、最大值、最小值。
- 后续可能需要长期趋势分析。

TimescaleDB 基于 PostgreSQL 扩展，适合存储和分析时序数据。

## 7. MQTT Topic 设计

系统使用结构化 topic：

```text
smartpot/{device_id}/telemetry
smartpot/{device_id}/status
smartpot/{device_id}/event/watering
smartpot/{device_id}/event/alarm
smartpot/{device_id}/command/water
smartpot/{device_id}/command/photo
smartpot/{device_id}/command/config
smartpot/{device_id}/command/sync
smartpot/{device_id}/response/water
smartpot/{device_id}/response/photo
smartpot/{device_id}/response/config
smartpot/{device_id}/response/sync
```

设计优点：

- 以设备 ID 隔离不同设备。
- telemetry、status、command、response、event 语义清晰。
- 后端可以用通配符订阅，如 `smartpot/+/telemetry`。
- 便于扩展新命令和新事件。

## 8. 关键技术点

### 8.1 异步后端

FastAPI 与 SQLAlchemy Async 结合，提高并发处理能力。MQTT handler、WebSocket 推送、后台 worker 都采用异步模式，适合物联网场景中大量设备持续上报数据的需求。

### 8.2 设备在线状态时效判断

项目不是简单依赖 MQTT retained 状态，而是加入 `last_seen_at` 心跳时间，避免设备断电后仍显示在线。这是物联网系统中非常实际的可靠性优化。

### 8.3 MQTT + HTTP 混合通信

系统没有把所有数据都塞进 MQTT，而是：

- MQTT：遥测、命令、状态、事件。
- HTTP：图片上传、REST API 管理。

这种设计符合实际物联网系统的通信分层思想。

### 8.4 多端统一 API

Web 前端和 Android App 复用同一套后端 REST API：

- 降低接口维护成本。
- 保证多端数据一致性。
- 后端作为唯一业务规则中心。

### 8.5 运行时配置下发

固件不再只依赖编译期宏，而是通过 MQTT config 指令接收后端配置。这样可以动态调整：

- 自动补水开关。
- 土壤湿度补水阈值。
- 默认补水时长。
- 温度保护阈值。

这是从“静态固件”向“云端可配置设备”的升级。

### 8.6 植物品种驱动的个性化养护

不同植物有不同的适宜环境和补水策略。项目通过 plant_types 表维护植物品种参数，使系统可以根据植物类型自动调整养护规则。

这比固定阈值更智能，也更贴合真实养护场景。

### 8.7 命令 ACK 与超时机制

后端下发命令后会创建 Command 记录，并等待设备响应。如果超时未响应，则将命令状态置为 timeout。

这个机制可以回答“如何知道设备是否执行了命令”这一类答辩问题。

### 8.8 WebSocket 实时推送

用户不需要不断刷新页面。后端在遥测更新、告警产生、命令状态变化时通过 WebSocket 推送给前端。

### 8.9 Mock 模式

固件支持 Mock 模式：

- 摄像头返回假图像。
- 传感器返回模拟值。
- ADC 返回随机值。
- 所有接口可用。

这解决了“无硬件情况下预开发”的问题，提高开发效率。

### 8.10 图像识别与大模型建议结合

系统不仅展示传感器数据，还结合病害识别和大模型建议生成养护报告，体现智能化应用价值。

## 9. 项目实现中的关键问题与解决方案

### 9.1 前端病害表格无法显示

可能原因：

- 后端时间格式不兼容。
- 前端对空数组或异常数据处理不足。

解决思路：

- 后端统一 ISO 时间解析和格式化。
- 前端对接口返回数组做兜底处理。
- 表格增加错误提示和滚动配置。

### 9.2 设备没有设备码如何新增设备

解决方案：

- 使用局域网发现机制。
- ESP32 提供本地 HTTP `/api/status`。
- 后端扫描同一 WiFi 网段。
- 用户选择发现到的设备进行绑定。

为什么优先 WiFi 而不是 BLE：

- ESP32 和电脑/后端已在同一 WiFi。
- 后端可以直接扫描并绑定。
- 不需要手机蓝牙权限和 BLE 配网流程。
- 对毕业设计演示更稳定。

BLE 适合初始配网场景，但本项目设备已入网，因此 WiFi 发现更简单可靠。

### 9.3 设备断电后仍显示在线

原因：

- 只依赖 MQTT online 状态或数据库 online 字段，会出现状态滞后。

解决：

- 增加心跳字段 `last_seen_at`。
- 设备每 30 秒上报 status。
- 后端超过 75 秒未收到心跳则判定离线。

### 9.4 Android Gradle 构建问题

遇到的问题包括：

- Gradle Kotlin DSL source 下载失败。
- JVM target 不一致。
- JDK 17 toolchain 下载失败。
- Kotlin 1.9.25 与 kotlinx.serialization 版本不兼容。

解决：

- 使用 Groovy Gradle 文件替代 Kotlin DSL，降低下载依赖。
- Java/Kotlin target 统一。
- 避免自动下载 toolchain。
- 将 kotlinx.serialization-json 调整到兼容 Kotlin 1.9.25 的版本。

### 9.5 LoginData 缺少 expires_at

Android 解析登录响应时报错：

```text
Field 'expires_at' is required
```

解决：

- Android 数据模型将 `expires_at` 设置为可空。
- 后端登录接口也补充返回过期时间。

### 9.6 自动补水阈值不同步

现象：

- 用户将植物品种补水阈值改为 1%。
- 土壤湿度 20% 仍自动补水。

原因：

- 后端自动补水读取植物品种阈值，不会触发。
- 但固件本地自动补水仍使用固定宏 25%。

解决：

- 新增固件 `runtime_config`。
- 固件本地自动补水改为读取运行时阈值。
- 后端在设备绑定品种、修改品种补水配置、设备上线时下发 config。
- 固件默认关闭本地自动补水，避免未收到配置时误补水。

这是项目中非常重要的系统一致性问题，适合写入论文“调试与优化”章节。

## 11. 答辩可能被问到的问题与回答思路

### Q1：为什么使用 ESP32-S3？

ESP32-S3 具备 WiFi 通信能力、较强的计算能力、较多 GPIO，并且支持摄像头接口，适合连接 OV2640、DHT11、BH1750、土壤湿度传感器和水泵等外设。相比普通单片机，它更适合物联网应用。

### Q2：为什么用 MQTT？

MQTT 是轻量级发布订阅协议，非常适合物联网设备。设备端只需要发布遥测数据和订阅控制命令，后端可以通过 topic 通配符管理多设备。相比轮询 HTTP，MQTT 延迟更低，网络开销更小。

### Q3：为什么图片不用 MQTT 传？

图片体积较大，而 MQTT 更适合轻量消息。如果用 MQTT 传图片，容易出现包大小限制、重传复杂和 broker 压力增加等问题。因此本项目使用 HTTP multipart 上传图片，MQTT 只负责拍照命令。

### Q4：如何判断设备是否在线？

设备每 30 秒发送一次 status 心跳，后端记录 `last_seen_at`。如果超过 75 秒没有收到心跳，即使数据库中 online 字段为 true，也判定为离线。

### Q5：如何避免设备断电后仍显示在线？

使用心跳时效机制，不只依赖 retained MQTT 状态。断电后设备停止发送心跳，后端会在超时时间后判定离线。

### Q6：自动补水如何实现？

系统有云端和本地两层自动补水。云端根据最新遥测和植物品种阈值判断是否下发补水命令；固件本地根据运行时配置做兜底判断。为避免重复补水，后端设置冷却时间，固件也设置水泵冷却保护。

### Q7：为什么要有植物品种管理？

不同植物对水分、温度和湿度需求不同。植物品种管理使系统可以按品种设置不同阈值，而不是使用统一固定参数，提高养护准确性。

### Q8：如果修改植物品种阈值，设备如何同步？

后端在修改植物品种或给设备设置植物品种时，会通过 MQTT config 命令下发新的自动补水阈值到设备。设备固件接收后更新运行时配置。

### Q9：如何防止频繁补水？

后端自动补水 worker 有冷却时间限制。固件水泵模块也有冷却时间和最大运行时长限制，避免水泵频繁启动或长时间运行。

### Q10：Web 和 App 是否是两套后端？

不是。Web 和 Android App 共用同一套 REST API 和认证机制，只是 UI 展示不同。这样可以保证数据一致性，也降低后端维护成本。

### Q11：系统如何处理命令执行结果？

后端下发命令时创建 Command 记录。设备执行命令后通过 MQTT response topic 返回执行结果。后端更新命令状态，并通过 WebSocket 推送给用户端。如果 30 秒未响应，则命令超时。

### Q12：病害检测如何实现？

设备上传植物照片后，后端图像处理 worker 使用 YOLOv11 ONNX 模型进行推理，输出病害类别、置信度和边界框。检测结果保存到数据库，并在高风险情况下生成告警。

### Q13：如果 YOLO 模型不可用怎么办？

系统设计了回退逻辑，可以使用规则检测生成低置信度结果，保证演示和业务链路不中断。

### Q14：为什么使用 FastAPI？

FastAPI 支持异步、类型注解、自动文档和依赖注入，适合构建高性能 API 服务。同时它和 Pydantic、SQLAlchemy Async 配合较好。

### Q15：为什么 Android 使用 Jetpack Compose？

Jetpack Compose 是现代 Android 声明式 UI 框架，代码结构更简洁，适合快速构建具有复杂状态和视觉风格的移动端界面。

### Q16：项目有哪些安全设计？

用户端使用 JWT 鉴权，接口通过当前用户校验设备归属。设备操作必须先验证设备属于当前用户，避免用户控制他人设备。

### Q17：如何扩展多设备？

设备 ID 是 topic 和数据库记录的核心标识。MQTT topic 使用 `smartpot/{device_id}/...` 格式，后端可以通过通配符订阅所有设备消息，天然支持多设备扩展。

### Q18：系统的不足是什么？

可以从以下方面回答：

- 当前设备端配置主要存储在内存，断电后需要后端重新下发。
- 图像识别模型精度依赖训练数据规模。
- 自动补水还可以结合水箱液位、天气、植物生长阶段进一步优化。
- 局域网发现依赖同一 WiFi 网络，跨网段场景需要额外方案。

### Q19：后续如何改进？

可以加入：

- BLE 配网。
- 设备配置持久化到 NVS。
- 更完善的 OTA 升级。
- 更高精度土壤湿度校准。
- 多用户共享设备。
- 更复杂的病害识别模型和知识库。
- 使用消息队列解耦图像处理任务。
