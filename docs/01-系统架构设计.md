# 01 — 系统架构设计

## 1. 架构总览

采用 **端—云—用户端** 三层协同架构：

```
                          ┌─────────────────────────────┐
                          │        用户端 (Android)        │
                          │  ┌─────┐ ┌──────┐ ┌───────┐  │
                          │  │数据  │ │病害  │ │养护建议│  │
                          │  │可视化│ │告警  │ │与控制  │  │
                          │  └─────┘ └──────┘ └───────┘  │
                          └──────────────┬──────────────┘
                                         │ REST API (HTTPS)
                          ┌──────────────┴──────────────┐

                          │  ┌──────────────────────┐    │
                          │  │   API Gateway (Nginx) │    │
                          │  └──────────┬───────────┘    │
                          │  ┌──────────┴───────────┐    │
                          │  │  FastAPI 业务服务     │    │
                          │  │  • 用户/设备管理       │    │
                          │  │  • 数据读写            │    │
                          │  │  • 控制指令转发        │    │
                          │  └──────────┬───────────┘    │
                          │  ┌──────────┴───────────┐    │
                          │  │   模型推理服务          │    │
                          │  │  • YOLOv11 病害检测    │    │
                          │  │  • LLM 养护策略推荐    │    │
                          │  └──────────┬───────────┘    │

                          │  │  • PostgreSQL+Timescale│    │
```

## 2. 三大模块职责

### 2.1 设备端 (ESP32-S3)

| 功能模块 | 描述 |
|---------|------|
| 传感器采集 | 每 5 分钟采集一次温湿度(DHT22)、土壤湿度(ADC)、光照(BH1750) |
| 自动补水 | 本地安全逻辑 + 云端阈值，PWM 控制微型水泵，记录补水行为 |
| 定时拍照 | 每日 08:00 / 12:00 / 16:00 定时触发，连拍 3 张选优，环形补光 LED 辅助 |
| MQTT 通信 | 上报遥测数据、设备状态；接收控制/配置指令 |
| HTTPS 上传 | 图像以 multipart/form-data 直接 POST 到云端，不在 MQTT 中传输二进图片 |
| OTA | 接收云端下发的固件升级指令与 URL |
| 安全保护 | 水泵防干烧、过流保护、连续运行超时强制停止 |

### 2.2 云端服务器

| 功能模块 | 描述 |
|---------|------|
| MQTT Broker | EMQX，负责设备接入、消息路由、Session 管理 |
| 设备管理服务 | 设备注册/绑定/解绑、在线状态、配置管理 |
| 数据接入服务 | 订阅设备遥测 Topic → 解析 → 写入 TimescaleDB + 实时推送 |
| 图像处理流水线 | 接收图片 → 存储到 MinIO → 调用 YOLOv11 推理 → 写入检测结果 |
| YOLOv11 推理 | ONNX/TensorRT 部署，输出病害类别、置信度、边界框 |
| LLM 养护策略 | 读取最近 N 天传感器历史 → 拼接 prompt → 调用大模型生成养护建议 |
| API 服务 | FastAPI REST 接口，供 App 调用 |
| 告警服务 | 病害检测触发 → 写入告警表 → APNs/FCM 推送 |

### 2.3 用户端 (Android App)

| 功能模块 | 描述 |
|---------|------|
| 数据可视化 | 实时数值卡片 + 历史折线图 (温湿度、土壤湿度、光照) |
| 病害识别展示 | 标注后的叶面图片 + 病害类别、置信度、建议措施 |
| 告警列表 | 病害告警、设备离线告警、水位不足告警 |
| 日报/周报 | 云端生成的统计报告，含环境趋势与养护评分 |
| 手动控制 | 补水按钮（设置时长）、立即拍照按钮 |
| 设备管理 | 添加/删除设备、修改植物品种、查看在线状态 |
| 品种预设 | 常见绿植养护参数数据库，选择后自动同步阈值到云端 |

## 3. 数据流

### 3.1 传感器数据流

```
ESP32 采集 → JSON 序列化 → MQTT Publish (QoS 1)
           → EMQX Broker → 后端订阅消费 → TimescaleDB 写入
           → Redis Pub/Sub → WebSocket 推送给在线 App 用户
```

### 3.2 图像数据流

```
ESP32 拍照 → 本地质量评分 → 选最优 1 张
          → HTTPS POST /api/devices/{id}/images
          → API Gateway → FastAPI 接收
          → 存入 MinIO → 写入图片记录(DB)
          → 异步调用 YOLOv11 推理服务
          → 检测结果写入 DB + MinIO (标注图)
          → 若检测到病害 → 写入告警表 → 推送通知
          → MQTT Publish 结果摘要到设备 Topic
```

### 3.3 控制指令流

```
App → POST /api/devices/{id}/water → FastAPI 接收
    → 写入指令记录表 → 通过 EMQX REST API 发布到设备 Topic
    → ESP32 收到指令 → 执行 → 返回 ACK (MQTT)
    → 后端收到 ACK → 更新指令状态 → App 轮询/WebSocket 获取结果
```

## 4. 关键设计决策

1. **图片不走 MQTT**：图片较大（数百 KB），MQTT 消息体不宜过大。采用 HTTPS 直传方案，MQTT 仅用于通知图片已上传或返回检测摘要。
2. **命令 ACK 机制**：所有云端→设备指令均需设备回复 ACK，超时 30s 视为失败并通知用户。
3. **本地安全优先**：自动补水逻辑在 ESP32 本地也有备份（长时间无云端指令时按保守阈值执行），避免断网导致植物干枯。
4. **App 不直连硬件**：Android App 仅与云端 API 交互，降低安全风险并简化 App 逻辑。
